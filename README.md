# Кандидатогенерация для поиска услуг Авито

По поисковому запросу нужно отобрать из корпуса benchmark_items (189 212 объявлений) **до 50 кандидатов**, которые дальше уйдут на ранжирование. Метрика - Recall@50: какая доля нужных объявлений попала в эти 50. Порядок внутри 50 на метрику не влияет.

Результат: Recall@50 = **0,928** на офлайн-валидации. Простой baseline даёт 0,829.

Файл для отправки - `answer.csv` в корне репозитория, его создаёт `python -m src.predict logreg`.

## Как запустить

Использовался Python 3.13

```bash
pip install -r requirements.txt
```

Файлы `train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet` добавить в `dataset/`.
Затем по порядку:

| Шаг | Команда |
|---|---|
| 1. Разбиения val и rank | `python -m src.split` |
| 2. Эмбеддинги e5 (кешируются) | `python -m src.dense e5 val rank bench` |
| 3. Пулы кандидатов с признаками | `python -m src.pools` |
| 4. Обучение слияния и сравнение способов | `python -m src.fusion` |
| 5. Итоговый answer.csv | `python -m src.predict logreg` |

В репозитории уже лежат обученная модель слияния (`artifacts/fusion_logreg.joblib`,
`artifacts/fusion_weighted.json`) и файлы разбиений, поэтому шаги 1, 3 и 4 можно пропустить с целью экономии времени.
Модель сохранена через joblib и привязана к версии scikit-learn из `requirements.txt`: если при
загрузке появится предупреждение или ошибка, достаточно заново выполнить шаги 3 и 4 - обучение занимает секунды.

Отдельно (нужны для цифр из разделов ниже, на сам ответ не влияют):
- `python -m src.baseline` - baseline и сравнение его вариантов;
- `python -m src.eval_sources e5` - оценка каждого источника.

Модель e5 скачивается с HuggingFace один раз. Дальше она грузится только из локального кеша: прогон с `HF_HUB_OFFLINE=1` даёт тот же результат, обращений к внешним сервисам нет.

Самый долгий шаг - кодирование корпуса (около 70 минут на CPU у меня заняло). Чтобы его пропустить, можно скачать уже посчитанные эмбеддинги и положить оба файла в папку `artifacts/`:

- [ссылка на диск](https://drive.google.com/drive/folders/1yjtPUR8O8zF5VCylIDZXwA0yj88Wpw3I?usp=sharing) — `emb_e5.npy` и `emb_e5_ids.parquet`

## Как устроено решение

```
запрос (текст, локация, фильтры, категория)
   │
   ├─ 1. Семь источников кандидатов, каждый даёт свои 100 объявлений
   │     BM25 по тексту · n-граммы · эмбеддинги e5 · 3 источника по логам train
   │     у каждого источника скор дополняется гео-приором: log P(локация объявления | локация поиска)
   │
   ├─ 2. Пул: объединение источников, > 50 кандидатов на запрос
   │
   └─ 3. Слияние: логистическая регрессия выбирает из пула 50 и кладёт в answer.csv
```

### Пояснения

**Использование нескольких источников:** поиск устроен поэтапно: первый этап отвечает за полноту, второй - за порядок. Если объявление не попало в 50 кандидатов, ранжирование его уже не вернёт, поэтому важна полнота. Также разные способы поиска могут ошибаться по-разному

**Пул** - это объединение списков всех источников на один запрос. Из него слияние выбирает 50 для ответа. Полнота пула - это верхняя граница: чего нет в пуле, того не будет и в ответе. Потери в нём делятся на два типа: объявление не нашли источники ( 4,2% ), нашли, но слияние не взяло в топ-50 ( 3,0% ).

**Почему гео-локация приоритетнее, чем фильтр:** в 83% случаев выбранное объявление в той же локации, что и поиск (из eda.ipynb), но и отбросить остальные нельзя, часть подходящих теряется. Около 7% нужных объявлений не попадают в пул: исполнители из соседнего города, а также «региональные» запросы (область, «вся Россия»), где у локации поиска вообще нет своих объявлений. Поэтому локация даёт не запрет, а штраф к скору: объявление издалека всё ещё может пройти, если сильно лучше по тексту.

## 1. Данные и признаки

Решение основано на наблюдениях в `notebooks/eda.ipynb`. Ещё раз повторю, что было выявлено и какие из этого сделаны выводы:

| Что видно в данных | Что из этого следует |
|---|---|
| Объявление в той же локации, что и поиск (83% случаев); иначе обычно рядом (медиана 34 км) | location - самый сильный сигнал: без него Recall@50 падает с 0,83 до 0,35 |
| Лишь 37% текстов benchmark встречались в train; 90% объявлений корпуса в логах не встречаются | Запоминать конкретные пары «запрос - объявление» бесполезно, нужно выявлять общие связи |
| Все слова запроса есть в заголовке меньше чем у половины пар, с описанием - у 82% | Искать нужно по всем полям (title, infm_param, description) и с учётом морфологии |
| По одному тексту запроса 93% выборов приходится на одну подкатегорию | Подкатегорию можно предсказать по похожим запросам |
| Фильтры есть у 67% поисков train и только у 37% запросов benchmark | Валидация должна повторять распределение benchmark |

**Из запроса (benchmark_queries) используются:** текст, локация, текст фильтров (совпадение с параметрами объявления), категория (признак «категория 0»). 

Флаг доставки не используется: в benchmark он везде 0.

**Из объявления (benchmark_items):** заголовок, параметры, описание, локация и координаты, подкатегория, рейтинг, число отзывов, цена, флаги «телефон скрыт» и «сообщения запрещены».

**Из логов train:** похожие запросы и что по ним выбирали; P(локация объявления | локация поиска); популярность подкатегории

**Признаки кандидата (54 шт), сгруппированы так:** скоры всех источников и их нормировки; флаги «попал в топ источника» и сколько источников его нашли; BM25 по каждому полю; доля слов запроса в заголовке и описании; совпадение с фильтрами; гео (вероятность, та же ли локация, км, локальность подкатегории); свойства объявления; свойства запроса.

## 2. Модели и алгоритмы

### Источники кандидатов (`src/sources.py`)

1. **BM25 по полям** заголовок / параметры / описание с весами 1 / 0,3 / 0,3. Реализация на
   разреженных матрицах. Слова приводятся к словарной форме через pymorphy3.
   BM25 - стандартная формула текстового поиска: слово даёт тем больше, чем оно реже во всём
   корпусе и чаще в документе, с поправкой на длину документа.
2. **TF-IDF по символьным n-граммам** заголовка (по 3–5 символов). Нужен против опечаток и склеек: «автоподбор» и «авто подбор»  имеют общие куски букв, даже если слова не совпали.
3. **Эмбеддинги** [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small)
   без дообучения. Модель переводит тексты в векторы так, что близкие по смыслу оказываются рядом,
   и находит то, где нет общих слов с запросом. Выбрана потому, что обучена именно на парах
   «короткий запрос → документ», поддерживает русский, хватает CPU
4. **Три источника по логам:** для запроса находим 30 самых похожих текстов запросов train и
   смотрим, что по ним выбирали:
   - сами объявления (полезно редко: корпус почти весь новый);
   - распределение подкатегорий;
   - **расширение запроса**: слова из заголовков выбранных объявлений, по которым затем ищем
     BM25. Так решается проблема синонимов: по запросу «смм» подтягиваются «продвижение»,
     «соцсети», «таргет». Это источник с самым большим уникальным вкладом.
5. **Гео-локация**: log P(локация объявления | локация поиска), посчитанная по логам. Прибавляется к скору источника с весом бета, подобранным на валидации.

### Слияние: выбрать 50 из пула (`src/fusion.py`)

Реализованы три способа, чтобы проверить, какой сработает лучше и выбрать

| Способ | Что делает | Почему подходит | Drawbacks | Recall@50 |
|---|---|---|---|---|
| RRF (Reciprocal Rank Fusion) | складывает `1/(60 (default) + rank)` по всем источникам | не нужно обучение; работает с разными шкалами скоров, так как смотрит только на места | считает все источники одинаково надёжными | 0,865 |
| Взвешенная сумма | `Σ wᵢ · (скор_i / макс) + w_geo · log P(гео)`, 8 весов подобраны перебором | сильным источникам можно дать больше веса; веса видно глазами | видит только скоры, но не свойства объявления | 0,896 |
| **Логистическая регрессия** | `P(объявление выбрано) = σ(Σ w_j · x_j)` по всем признакам | самая простая обучаемая модель для ответа «да/нет»; обучается быстро; веса после стандартизации показывают, что важно | линейная: не ловит взаимодействия признаков | **0,928** |

Итоговый вариант - **логистическая регрессия**. Что у неё получилось важным:

| Признак | Вес |
|---|---|
| сходство e5 | +0,72 |
| доля слов запроса в описании | +0,54 |
| гео log P | +0,53 |
| сколько источников нашли объявление | +0,43 |
| длина описания | −0,39 |
| расстояние в км | −0,35 |

Это согласуется со здравым смыслом: объявление берут, если оно похоже по смыслу, содержит слова запроса, находится рядом и его нашли сразу несколько источников.

## 3. Как проверялось качество

**Валидация, повторяющая benchmark** (`src/split.py`). Из train отложено 3000 уникальных поисков («текст + локация + фильтры + категория», релевантные - выбранные в нём объявления. 

Повторены пропорции benchmark: 37% текстов знакомы, 63% - новые, доля запросов без фильтров такая же. Корпус валидации - benchmark_items + нужные объявления отложенных запросов, чтобы искать приходилось среди настоящих «чужих».

**Отдельная выборка для обучения слияния.** Второе разбиение `rank` (6000 поисков) сделано так же, но из остатка train. На нём подбираются веса и обучается регрессия, а `val` используется только для сравнения. 
Проверка на утечку встроена в код: новых текстов в обучающей части 0,00.

**Путь решения:**

| Вариации | Recall@50 |
|---|---|
| BM25 по всем полям + жёсткий гео-фильтр (baseline) | 0,829 |
| Гео - приор вместо фильтра (штрафует) + лемматизация | 0,859 |
| Пул источников + RRF | 0,865 |
| Пул + взвешенная сумма | 0,896 |
| Пул + логистическая регрессия без эмбеддингов (только классика) | 0,918 |
| **Пул + логистическая регрессия с multilingual-e5** | **0,928** |
| *Потолок: полнота пула* | *0,958* |


**Формат ответа** проверяется кодом (`src/submission.py`): две колонки, все query_id без повторов, не больше 50 id в строке, без повторов внутри строки, каждый id есть в корпусе и записан ровно как там (16 символов 0-9a-f).

**Воспроизводимость:** seed зафиксирован, сортировки стабильные, инференс на CPU. Повторные запуски `python -m src.predict logreg`, в том числе без сети, дают тот же `answer.csv`, что лежит в корне репозитория. Для сверки команда печатает md5 получившегося файла.

`submissions/answer_baseline.csv` создаётся командой `python -m src.baseline --submit`.

## 4. Ошибки и чтос  ними был сделано

| Ошибка | Как нашли | Что сделали |
|---|---|---|
| Жёсткий гео-фильтр отсекает нужные объявления | посчитали, сколько нужных объявлений переживает фильтр | заменили фильтр на log P, +0,03 |
| Нужное объявление не находит ни один источник (синонимы, перефразы) | 4,2% нужных объявлений вне пула | добавлены расширение запроса по логам и эмбеддинги |
| Слова запроса часто только в описании | сравнение источников по полям: описание дало +0,08 | ищем по всем полям, добавлен признак «доля слов запроса в описании» |
| Общие запросы в больших городах: совпадений сотни | срез по числу объявлений в локации | признаки рейтинга, популярности и согласия источников |
| У baseline 31 запрос получил меньше 50 кандидатов, один - вообще ноль | проверка answer.csv | пул из семи источников всегда даёт больше 50 |


**Что было рассмотрено, но не выбрано для итогового решения**

| Что | Результат | Решение |
|---|---|---|
| [deepvk/USER2-small](https://huggingface.co/deepvk/USER2-small) - русскоязычный энкодер | R@50 = 0,840 против 0,837 у e5, но вклад в пул почти полностью дублирует e5 (+0,002) | не берём: выигрыш в пределах шума, а кодирование корпуса втрое дольше (дольше двуз часов) |
| Стемминг Snowball вместо лемматизации | 0,856 против 0,859 | оставили лемматизацию, разница небольшая, статистически для русского языка предпочтительне лемматизация |
